# Privacy and sharing

The planner supports Shared and Private content for every trip. The owner controls visibility and optional access for named existing members. A read-only member can read shared content and specifically granted private content, but cannot edit either.

Use **More → Settings → Privacy & access** to review all record types, edit privacy, add a private note, preview the shared member experience, or change/remove member access. New invitations default to Read only. Creating an invitation retains the existing verified-email claim flow and does not send mail.

The preview is a server-filtered, read-only baseline member view with no private grants. It covers all normal tabs and tickets. It is suitable for reviewing a prospective member who will have no private grants. It does not impersonate another person's login or simulate a member with additional private grants.

## Scope

Activities, stays, bookings, tasks, decisions/notes, journeys and attachments each have `visibility` (default `shared`) and `private_user_ids` (default empty). Notes embedded in a record follow that record's visibility. Trip overview notes are shared; confidential trip notes belong in a Private decision/note.

Existing records retain their IDs. Where an ordinary record mixes shared and confidential details, retain the confidential details as a Private note and keep the ordinary record shared. Attachments containing group-wide external ticket/order links may need to remain Private even when the activity itself is Shared.

## Enforcement

- Restrictive SELECT/UPDATE/DELETE RLS policies supplement existing trip-membership and edit-role policies on all seven content tables.
- A non-exposed, fixed-search-path helper checks membership, owner/explicit access, every linked parent, and trip consistency. A private parent restricts its linked children even when they are individually Shared. Grant access to each required private parent as well as the child.
- Database triggers restrict visibility/access-list changes to the trip owner and reject cross-trip/inaccessible links. Member administration is owner-only; email addresses are returned only through an owner-checked directory.
- Public sharing retains the existing safe column projection. Its security-invoker view calls a non-exposed function that only returns Shared records with Shared parents for the already-public trip. It never returns notes, ticket payloads, references or private records. Anonymous raw-table access remains denied.
- Shared JSON exports and itinerary PNGs filter private records and linked descendants, including when generated by the owner. JSON import still creates a new trip; imported private access lists are cleared. Shared exports are not a complete backup of private content.
- The service worker caches the static shell only. Sign-out/view changes clear ticket state and image URLs. No private Supabase response is cached offline.

## Validation

`node japan-trip/privacy.test.mjs` exercises linked export filtering, all main view renderers, privacy forms, and read-only member/preview UI controls.

`supabase/test_privacy.sql` runs transactional database fixtures under actual `authenticated` and `anon` roles. It covers owner/viewer/editor/outsider isolation, editing restrictions, explicit private grants and revocation, inherited attachment privacy, owner-only preview, and public/raw-table separation. All fixture users, trips and memberships are rolled back.

The production data was separately audited under a temporary read-only membership, then rolled back. The public REST projection was checked through HTTP; raw anonymous reads were denied for all seven content tables. All pre-change record IDs were checked against the protected snapshot and remain present. No real invitation was created.

Supabase's post-change security advisor has no ERROR findings. The existing authenticated-only invitation-claim RPC warning is intentional. The pre-existing leaked-password-protection warning remains unrelated to record visibility.

Signed-in browser testing with separate real family accounts, physical iPhone/PWA testing and native iPhone file sharing remain acceptance checks. Database role tests do not substitute for those browser/device checks.

## Deployment and recovery

The app is served from the repository's `main` branch by GitHub Pages. Assets and the static-shell service worker have a new version to refresh installed clients.

The migration is additive. Before schema/data changes, `private.privacy_backups` captured all original content records, trip metadata, policies and public view definitions. This table is outside exposed schemas and grants no access to application roles. Private notes also retain the original mixed-content details for owner review.

The preceding Git commit is the frontend rollback point. Retain the database privacy protections when rolling back frontend assets. For data recovery, an administrator can retrieve the original row from `private.privacy_backups` by `kind` and `payload->>'id'`, compare it with the current row and restore the needed fields. Restoring confidential original notes into Shared rows would re-expose them; recover them into Private notes instead. Do not drop privacy columns/policies or restore the old public projection as a routine rollback.

## Save permission correction (8 November 2026)

The original privacy SELECT predicate re-read the target row through a STABLE helper. That row is not visible to the helper during INSERT ... RETURNING, so authenticated new-item saves incorrectly failed. The restrictive policies now authorise the candidate row's values directly with a non-exposed helper, while resolving linked parents through the existing protected lookup. Membership, owner/explicit grants, private-parent restrictions and write-role policies remain enforced. INSERT now has its own restrictive privacy check, and UPDATE checks the proposed row as well. Previous policy definitions were captured in the protected snapshot before migration.

The regression SQL now explicitly tests authenticated INSERT/UPDATE RETURNING for Shared and Private records across all seven content tables, plus editor insertion, private-insert denial and viewer-insert denial. These are rolled-back fixtures.
